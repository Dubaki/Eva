## 2. Паттерны ошибок и цепочки rework

### ЦЕПОЧКА 1: Кризис Subscription Gate (задачи 089→097) — 9 шагов подряд

Самая длинная и разрушительная цепочка проекта:

```
089 → Реализован Subscription Gate на фронтенде
090 → Статус не синхронизируется в БД — fix
091 → Изменения в БД вручную игнорируются — force-fix
092 → КРИТИЧЕСКИЙ АУДИТ: система сломана фундаментально
093 → ЭКСТРЕННЫЙ ОВЕРХОЛ: полная перепись auth-логики
094 → Фронтенд кеширует старый статус — KILL CACHE
095 → RLS блокирует все read-запросы — HOTFIX RLS
096 → Все ещё возвращает null — серверный дамп БД для отладки
097 → Итоговый фикс: синхронизация auth и кнопка приложения
```

**Первопричина:** Архитектурная ошибка — `profiles` защищена RLS, а API-роуты читали через `anon` ключ вместо `service_role`. Каждый «фикс» лечил симптом, не причину.

## 3. Неэффективные шаги и рекомендации

### 3.1 Архитектурные ошибки

| Проблема | Сколько задач потрачено | Рекомендация |
|---|---|---|
| RLS + anon key в API-роутах | 9 (цепочка 089-097) | **Решать в задаче на схему БД (006):** явно документировать какой ключ используется в каждом контексте. Service Role Key = только для серверных операций верификации. |
| Async без await / race conditions | 8 (цепочка 024-068) | **Требовать в каждой задаче на воронку:** список всех async-операций с явным указанием порядка await. Запрет на навигацию до подтверждения записи в БД. |
| start_param теряется между экранами | 10+ (рефералы) | **Ввести правило:** любой параметр, получаемый от Telegram SDK при инициализации, немедленно персистируется в localStorage в первом компоненте-обёртке. |

### 3.2 Операционные промахи

| Проблема | Рекомендация |
|---|---|
| Нет try/catch в webhook — ошибки проглатываются | **Стандарт кода:** все edge functions и API-роуты обязаны иметь top-level try/catch с console.error |
| Тесты на Windows, деплой на Linux (case sensitivity) | **Перед любой задачей с ассетами:** проверять пути через grep на точное совпадение регистра с файловой системой |
| Документация (BRIEF) не обновлялась 20+ задач | **Правило:** каждые 10 задач — mandatory brief review. Явно включать «обновить BRIEF» в задачи, меняющие архитектуру |
| Пропущенные номера, дубли, нестандартные имена файлов (020-022, 030, 041, 062×2 и др.) | **Причина:** потеря контекста между сессиями. **Решение:** номер задачи всегда `max(существующих) + 1`, проверять командой `ls tasks/done/ | sort` перед созданием |

### 3.3 Дублирующиеся / избыточные шаги

- **Многократные «финальные» задачи:** задачи 050, 068, 070, 077, 097 — все называются «финальными», но каждый раз возникает следующий «финальный» фикс. Признак: задача закрыта без реальной верификации.
- **«Полировка» без стабильного основания:** задачи 012, 042, 054, 069, 070 занимались UX-полировкой, пока core-логика была нестабильна. Порядок должен быть: стабильность → полировка.
- **Admin-панель строилась 8+ задач:** потому что не было upfront-спецификации. Единая задача с ADR (Architecture Decision Record) сократила бы цепочку вдвое.

## 4. Анализ формата логов и новый шаблон

### 4.1 Текущий формат

Все 129 файлов содержат **только постановку задачи**:
- `<context>` — описание ситуации
- `<task>` — пронумерованные шаги
- `<rules>` — ограничения

**Что отсутствует:**
- ❌ Дата и время завершения
- ❌ Что фактически было сделано (vs что просили)
- ❌ Какие файлы были изменены
- ❌ Верификация: прошёл ли build, линтер, ручное тестирование
- ❌ Побочные эффекты или что может сломаться
- ❌ Ссылка на коммит
- ❌ Классификация задачи (feat / fix / hotfix / etc.)

Единственный индикатор завершения — факт нахождения файла в `tasks/done/`.

### 4.2 Новый шаблон лога завершения

Добавляется в конец файла задачи при переносе в `done/`:

```markdown
---

## COMPLETION LOG

**Статус:** completed | partial | blocked  
**Дата завершения:** YYYY-MM-DD  
**Тип задачи:** feat | fix | hotfix | emergency | ui | infra | docs | db | refactor  
**Исполнитель:** Claude Code | Human | Mixed  

### Сделано
- [краткое описание фактически выполненных шагов, отличий от постановки]

### Изменённые файлы
- `path/to/file.ts` — что изменено (1 строка)

### Коммит(ы)
- `abc1234` — сообщение коммита

### Верификация
- [ ] `npm run build` — passed / failed
- [ ] Линтер — passed / failed  
- [ ] Ручное тестирование — yes / no / n/a

### Побочные эффекты / риски
- [что может сломаться или уже сломалось в результате этой задачи]

### Открытые вопросы
- [нерешённые проблемы, которые могут потребовать follow-up задачи]
```

**Почему эти поля:**
- `Тип задачи` — позволяет мгновенно посчитать rework rate в будущих ретро
- `Изменённые файлы` — устраняет необходимость `git log --stat` для поиска контекста
- `Побочные эффекты / риски` — главное поле для предотвращения цепочек типа 089-097
- `Открытые вопросы` — делает follow-up задачи явными, а не случайными
